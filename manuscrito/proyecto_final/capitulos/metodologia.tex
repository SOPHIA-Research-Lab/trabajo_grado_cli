\chapter{Metodología}\label{chap:metodologia}
Esta sección describe la estrategia integral seguida para desarrollar el sistema de clasificación holográfica, desde la curaduría del dataset hasta la validación estadística y la generación de reportes automatizados. La metodología se diseñó con el propósito de ser reproducible, interpretable y extensible.

\section{Descripción de los datos}
El repositorio primario está compuesto por dos colecciones heterogéneas capturadas con un mismo arreglo DLHM: \textit{dataset\_1} y \textit{dataset\_2}. Cada captura siguió protocolos de iluminación idénticos para preservar la comparabilidad y se almacenó junto a metadatos de fecha y operador. La primera contiene hologramas de eritrocitos sanos y falciformes provenientes de un banco de sangre local, mientras que la segunda reúne muestras adquiridas en condiciones controladas de laboratorio. Cada archivo está almacenado en formato PNG con resolución máxima de 4640\,×\,3506 píxeles y profundidad de color de 8 bits. En total se disponen 304 hologramas rotulados, distribuidos en 151 sanos y 153 falciformes. El etiquetado proviene de expertos hematólogos y se mantuvo la información de procedencia para permitir particiones estratificadas por sujeto cuando se requiera extender el estudio.

Adicionalmente se cuenta con un conjunto externo \textit{holograms} que incluye tres categorías de organismos ajenos a la sangre (esporas de \textit{Aspergillus}, diatomeas y partículas de la familia \textit{Poaceae}). Este repositorio se emplea exclusivamente para evaluar la detección de anomalías y simular la presencia de contaminantes o artefactos en la cadena de captura. Antes de cada corrida se verifica la integridad de los archivos mediante sumas de verificación y se documentan las versiones de cada lote de datos.

Para favorecer futuras ampliaciones, el repositorio se estructura con metadatos normalizados (origen, fecha, temperatura de captura) y se implementa control de acceso para preservar la anonimización de los donantes. Esta información facilita replicar experimentos, agregar nuevas cohortes e identificar sesgos potenciales asociados a procedencia o condiciones de medición.

\section{Unificación y preprocesamiento}
Para estandarizar la información, se implementó un módulo de unificación que crea un dataset consolidado bajo la estructura \texttt{data/unified}. El proceso contempla los siguientes pasos:
\begin{enumerate}
    \item \textbf{Normalización geométrica}. Las imágenes de \textit{dataset\_1} presentan variaciones de tamaño y desplazamiento del objeto. Se extrae un parche central del holograma y se redimensiona a 512\,×\,512 píxeles utilizando interpolación bilineal. Para \textit{dataset\_2}, cuyos hologramas ya se encuentran centrados, solo se ajusta el tamaño si difiere del requerido.
    \item \textbf{Codificación de clases}. Se homogeniza la nomenclatura de clases a \textit{Healthy} y \textit{SCD}, independientemente del nombre original de cada carpeta.
    \item \textbf{Control de calidad}. Se descartan archivos corruptos o vacíos y se registra un log de procesamiento con estadísticas por clase.
\end{enumerate}
El resultado es un directorio unificado listo para la extracción de características. Este procedimiento se ejecuta automáticamente cuando el usuario inicia el análisis desde la interfaz de línea de comandos.

Además, el módulo registra tiempos de ejecución, estadísticas de descarte y hashes de los archivos resultantes, lo que permite auditar el proceso y detectar desviaciones cuando se incorporan nuevas fuentes de datos. Esta bitácora de unificación ha sido útil para calibrar el comportamiento del montaje holográfico y documentar incidencias en campo.

\section{Extracción de características}
Sobre cada holograma normalizado se calculan 84 descriptores. Las etapas principales son:
\begin{itemize}
    \item \textbf{Filtrado y normalización}. Se aplican filtros de mediana y ecualización adaptativa de histograma (CLAHE) para mitigar ruido de fondo y realzar contrastes locales \cite{Singh2017}.
    \item \textbf{Características de textura}. Se calcula la matriz GLCM con distancia de cinco píxeles y ángulo cero. De esta matriz se derivan estadísticos como contraste, correlación, homogeneidad y energía \cite{Barburiceanu2021}. Además, se genera un histograma LBP con 24 puntos y radio de tres píxeles, del cual se extraen los primeros diez coeficientes.
    \item \textbf{Dominio frecuencial}. Se obtiene el espectro de magnitud mediante FFT y se agrupa la energía en anillos concéntricos (tres bandas). También se evalúan filtros de Gabor en múltiples orientaciones para captar anisotropías \cite{OConnor2020}.
    \item \textbf{Momentos y morfología}. Se calculan los siete momentos invariantes de Hu, la extensión, la solidez, la relación de ejes, el perímetro normalizado y la relación área-convexidad.
\end{itemize}
Cada conjunto de características se almacena en archivos de cache individuales para acelerar ejecuciones posteriores. Además, se generan histogramas de control que permiten inspeccionar la distribución de cada descriptor y detectar valores atípicos potenciales antes del entrenamiento. Las métricas intermedias se registran en un archivo de trazas que permite auditar el comportamiento del extractor.

El extractor está modularizado de forma que nuevas familias de descriptores puedan añadirse con mínima intervención; el tiempo promedio por holograma ronda los 0,45~s en CPU, por lo que la reutilización del cache reduce significativamente los ciclos de experimentación y evita recalcular transformadas costosas.

\section{Selección de características}
Aunque el vector de 84 características es manejable, se emplea un proceso de selección para priorizar atributos con mayor poder discriminante. Se adopta \textit{SelectKBest} con estadístico ANOVA $F$ para evaluar la diferencia de medias entre clases \cite{Pedregosa2011}. Dependiendo del modo de operación, el pipeline conserva las mejores 20 características (modo rápido) o hasta 50 (modo profundo). La selección se actualiza en cada ejecución para reflejar posibles variaciones en el dataset y permite interpretar cuáles descriptores físicos influyen más en la predicción.

Adicionalmente se analizan los conjuntos de características seleccionados en corridas consecutivas para estimar su estabilidad; aquellos atributos que aparecen de forma recurrente se documentan en el reporte final como candidatos robustos para estudios futuros o para su traducción a indicadores ópticos medibles.

\section{Análisis exploratorio y control de calidad}
Previo al entrenamiento se realiza un análisis exploratorio que incluye histogramas por característica, gráficas de dispersión proyectadas mediante análisis de componentes principales y evaluación de outliers mediante puntuaciones z robustas. Los resultados orientan ajustes en los parámetros de normalización y permiten detectar problemas de adquisición (por ejemplo, hologramas saturados o con iluminación desigual). El pipeline registra automáticamente estas inspecciones en un cuaderno electrónico, lo que facilita comparar ejecuciones y documentar decisiones correctivas.

Cuando el análisis exploratorio identifica desviaciones marcadas se detona un flujo de revisión manual y, de ser necesario, se excluyen temporalmente las imágenes afectadas hasta resolver la causa raíz. Este control temprano evita que artefactos triviales sesguen el entrenamiento o inflen las métricas de validación.

\section{Modelos y ensamble}
La etapa de entrenamiento comienza dividiendo el dataset en conjuntos de entrenamiento y prueba con proporción 80/20 y estratificación por clase. Sobre el conjunto de entrenamiento se entrenan cuatro modelos base: regresión logística regularizada, SVM con kernel radial, bosque aleatorio de 200 árboles y clasificador de gradiente boosting con 300 iteraciones. Los hiperparámetros se optimizan mediante búsqueda aleatoria y validación cruzada interna. Posteriormente, las probabilidades resultantes se combinan a través de votación blanda con pesos ajustados según la métrica ROC-AUC obtenida durante la validación.

El modo profundo activa la optimización exhaustiva de hiperparámetros mediante \textit{GridSearchCV}, incrementa el número máximo de características y extiende el tiempo de búsqueda. Los espacios de búsqueda consideran rangos amplios para parámetros como la regularización de la regresión logística, el parámetro $C$ y la anchura del kernel en la SVM, el número de estimadores en los bosques aleatorios y la tasa de aprendizaje del gradiente boosting. En contraste, el modo rápido deshabilita la optimización avanzada para reducir costos computacionales y acelerar el uso durante etapas de prueba.

Finalmente, el entrenamiento se automatiza con un control de semillas y una verificación de convergencia que detiene procesos divergentes; los logs almacenan las configuraciones óptimas de cada modelo para facilitar su replicación o su despliegue en producción.

\section{Planteamiento matemático del clasificador}
Sea $D = \{(\mathbf{x}_i, y_i)\}_{i=1}^{n}$ el conjunto de entrenamiento, donde $\mathbf{x}_i \in \mathbb{R}^{p}$ representa el vector de características extraído del holograma y $y_i \in \{0,1\}$ denota la etiqueta (0 para Healthy, 1 para SCD). Cada clasificador base produce una probabilidad $p_m(y=1\mid \mathbf{x})$. El ensamble combina estas salidas mediante votación blanda ponderada:
\begin{equation}\label{eq:ensemble-prob}
\hat{p}_{\text{ens}}(y=1\mid \mathbf{x}) = \frac{\sum_{m=1}^{M} w_m\, p_m(y=1\mid \mathbf{x})}{\sum_{m=1}^{M} w_m},
\end{equation}
donde $w_m$ es el peso asignado al clasificador $m$ proporcional a su AUC durante la validación cruzada y $M=4$ en este proyecto. La predicción final se obtiene evaluando $\hat{p}_{\text{ens}}$ contra un umbral $\tau$ (por defecto, $\tau=0{,}5$).
La regresión logística calcula $p_1(y=1\mid \mathbf{x})$ como $\sigma(\mathbf{w}^{\top}\mathbf{x} + b)$, con la función sigmoide $\sigma(z) = 1/(1+e^{-z})$. Sus parámetros $(\mathbf{w}, b)$ se optimizan maximizando la log-verosimilitud penalizada descrita en el Capítulo~\ref{chap:marco}. La máquina de soporte vectorial genera un valor de decisión $f(\mathbf{x})$ que se transforma en probabilidad mediante calibración logística (sigmoid fitting) \cite{Bishop2006}. Para los bosques aleatorios, $p_3(y=1\mid \mathbf{x})$ corresponde al promedio de los votos positivos emitidos por cada árbol del conjunto. En el gradiente boosting, la probabilidad se obtiene aplicando la función logística al puntaje agregado $F(\mathbf{x}) = \sum_{t=1}^{T} \gamma_t h_t(\mathbf{x})$, donde cada $h_t$ es un árbol débil ajustado sobre los residuos de la iteración anterior \cite{Friedman2001}. Estas definiciones aseguran que las salidas de todos los clasificadores sean compatibles para la votación blanda.
La matriz de confusión y las métricas derivadas se calculan con las etiquetas finales $\hat{y} = \mathbb{I}[\hat{p}_{\text{ens}} \geq \tau]$. Asimismo, las probabilidades se almacenan para cada muestra a fin de calcular medidas de incertidumbre, como la desviación estándar entre clasificadores base y las curvas ROC. Este planteamiento matemático facilita la auditoría del sistema y la comparación con modelos alternativos; en particular, permite cuantificar la contribución de cada modelo al desempeño global y diagnosticar desacuerdos internos.

Esta formalización también deja abierta la posibilidad de integrar funciones de pérdida ponderadas o criterios de decisión adaptativos, elementos que se explorarán cuando se incorporen nuevas clases diagnósticas o se traslade el sistema a entornos clínicos con requisitos regulatorios específicos.

\section{Validación y métricas}
El rendimiento del sistema se estima con diversos indicadores. Durante la fase de entrenamiento se calcula la exactitud en el conjunto de prueba separado (20\%). Para evaluar la robustez se emplea validación cruzada estratificada de cinco pliegues, reportando promedio y desviación estándar de exactitud y AUC. Finalmente, se ejecuta validación Leave-One-Out sobre todo el conjunto para analizar el impacto de cada muestra individual \cite{Vabalas2019,Tsamardinos2022}. Las métricas complementarias incluyen sensibilidad, especificidad, precisión, F1 y curva ROC. En escenarios clínicos, la sensibilidad se interpreta como la capacidad de detectar correctamente pacientes con anemia falciforme, mientras que la especificidad refleja la probabilidad de clasificar como sanas a las células normales. Los resultados se guardan en archivos CSV y se representan con figuras generadas automáticamente en la carpeta \texttt{results}.

Como parte del flujo de trabajo, cada ejecución genera un resumen textual que contextualiza las métricas y ofrece recomendaciones sobre umbrales operativos, aportando evidencia adicional para la toma de decisiones clínicas.

Para claridad, se emplean las definiciones estándar: la exactitud se calcula como $\mathrm{Acc} = (\mathrm{TP}+\mathrm{TN})/(\mathrm{TP}+\mathrm{TN}+\mathrm{FP}+\mathrm{FN})$, la sensibilidad como $\mathrm{Sens} = \mathrm{TP}/(\mathrm{TP}+\mathrm{FN})$ y la especificidad como $\mathrm{Esp} = \mathrm{TN}/(\mathrm{TN}+\mathrm{FP})$. La métrica F1 se obtiene a partir de $2\cdot \mathrm{Prec}\cdot \mathrm{Sens}/(\mathrm{Prec}+\mathrm{Sens})$, donde $\mathrm{Prec}$ denota la precisión positiva. Para cada pliegue se almacenan tanto los valores puntuales como los intervalos de confianza a 95\%, estimados mediante bootstrap sobre las predicciones. Estos intervalos se reportan en el capítulo de resultados para contextualizar la variabilidad inherente a datasets pequeños.

\section{Plan experimental y modos de ejecución}
Los experimentos se organizaron en tres modos: rápido, completo y profundo. El modo rápido prioriza tiempos de respuesta cortos al limitar el número de características a 20 y desactivar la optimización exhaustiva de hiperparámetros; se utiliza durante el desarrollo y en verificaciones de integridad del pipeline. El modo completo mantiene los parámetros por defecto de `config.yaml` y se emplea para corridas rutinarias con equilibrio entre tiempo de ejecución y profundidad analítica. El modo profundo amplía la búsqueda de hiperparámetros, aumenta el número de características a 50 y ejecuta validaciones adicionales como Leave-One-Out y análisis de estabilidad. Cada modo genera reportes etiquetados por fecha y sello horario que documentan el conjunto de configuraciones empleadas, los resultados obtenidos y las rutas de los artefactos generados, lo cual permite reproducir cualquier análisis y comparar iteraciones de manera sistemática.

La agenda experimental se gestiona mediante plantillas semanales donde se registran hipótesis, datos utilizados y responsables, lo que asegura trazabilidad y evita reutilizar sin control los mismos conjuntos de prueba.

\section{Detección de anomalías}
Una vez entrenado el clasificador, se ajusta un detector de anomalías basado en la distancia de Mahalanobis \cite{Mahalanobis1936}. El modelo calcula la media y la matriz de covarianza sobre las características seleccionadas. El percentil 95 de las distancias observadas durante el entrenamiento define el umbral de activación. Cuando un holograma nuevo supera dicho valor, se marca como anomalía y se le asocia un \textit{score} normalizado entre 0 y 1. Para aumentar la explicabilidad se generan rankings de contribución de cada característica a la anomalía, lo que ayuda a evaluar si la desviación proviene de texturas inusuales, cambios geométricos o energía frecuencial atípica.

El conjunto externo de hologramas no sanguíneos se procesa en modo validación, registrando la distancia de Mahalanobis y la predicción del clasificador principal. Se espera que las muestras ajenas al dominio obtengan altas distancias y sean etiquetadas como anomalías, independientemente de la clase resultante. Esta prueba simula la presencia de polvo, células de otras especies o artefactos ópticos.

En un despliegue operativo, el umbral puede ajustarse en función de los requisitos de sensibilidad; por ello, el reporte incluye una tabla que sugiere valores alternativos y explica el impacto esperado en la tasa de falsos positivos.

\section{Automatización e interfaz}
Todas las etapas se encapsularon en una interfaz de línea de comandos documentada en \texttt{cli.py}. El usuario puede invocar modos rápidos, completos o profundos y generar reportes individuales de imágenes. El script \texttt{run\_analysis.py} automatiza el pipeline completo, mientras que \texttt{example\_single\_prediction.py} ofrece una guía de uso programático. Los resultados se centralizan en la carpeta \texttt{results}, que almacena métricas, visualizaciones, reportes y el modelo entrenado. La documentación adicional se distribuye en archivos Markdown para acelerar la incorporación de nuevos colaboradores.

La arquitectura de la interfaz se organiza en comandos modulares y pruebas funcionales básicas que garantizan respuestas coherentes ante parámetros inválidos, lo que mejora la robustez del software y simplifica su mantenimiento.

\section{Infraestructura de ejecución y reproducibilidad}
Todos los experimentos se realizaron en un equipo de escritorio con procesador de ocho núcleos a 3,2~GHz, 16~GB de memoria RAM y sistema operativo basado en GNU/Linux. Se creó un entorno virtual de Python 3.13 para aislar dependencias y garantizar la portabilidad del proyecto. Las librerías principales incluyen NumPy, Pandas, scikit-learn, scikit-image, OpenCV, Matplotlib y Seaborn \cite{Pedregosa2011}. Cada versión de librería se documentó en el archivo \texttt{requirements.txt} y se verificó su compatibilidad antes de ejecutar los experimentos finales.

Se empleó control de versiones con Git para rastrear cambios y se generaron etiquetas asociadas a hitos claves (prototipo inicial, optimización de hiperparámetros, integración del detector de anomalías). Los reportes automáticos se almacenan con marcas temporales, lo que facilita reconstruir el estado del sistema en un momento determinado. Para reforzar la reproducibilidad, se fijaron semillas de aleatoriedad en scikit-learn y NumPy.

Además, se documentó un procedimiento para recrear el entorno mediante contenedores ligeros o servicios en la nube, de modo que colaboradores externos puedan replicar los experimentos sin depender del hardware local.

\section{Gestión de riesgos y calidad}
La metodología incorporó puntos de control para mitigar riesgos experimentales. Antes de cada ejecución se validó la integridad del dataset unificado y se verificó la disponibilidad de espacio en disco para almacenar resultados. Una suite de pruebas unitarias sencillas comprobó la correcta creación del cache y la respuesta del detector ante entradas simuladas. Asimismo, los resultados anómalos detectados durante las fases piloto se documentaron en un cuaderno electrónico que acompaña este repositorio. Se mantiene un plan de mejora continua que prioriza riesgos críticos, revisa periódicamente el rendimiento y propone acciones de mitigación cuando se detectan desviaciones en métricas clave.
